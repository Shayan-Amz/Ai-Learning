# نقشه‌راه یادگیری AI و Agentها

> **اولویت فعلی:** هدف اصلی یادگیری و ساخت یک Agent ابزارمحور است؛ پروژه‌ی فعلی Local Research Agent است و کد آن باید هم‌زمان با ساخت، مرحله‌به‌مرحله توضیح داده شود. درس‌های toy فعلاً متوقف‌اند و Pathfinder کانادا فقط prototype قبلی/اختیاری است، نه هدف اصلی. این نقشه‌راه و درس‌های قبلی آرشیو/مرجع می‌مانند.

## هدف و وضعیت شروع

این مسیر برای کسی طراحی شده که هم‌زمان آیلتس می‌خواند، مقصد فعلی‌اش کاناداست و می‌خواهد مهارت‌های AI کاربردی بسازد؛ نه این‌که چندین فریم‌ورک را سطحی حفظ کند.

**پروفایل فعلی تو:** Python = ۳ از ۵، Git = ۱ از ۵، API = صفر، Windows، حداقل ۱۲ ساعت در هفته، علاقه‌مند به کانادا. این‌ها خودارزیابی‌اند؛ در هفته‌ی اول با چند تمرین کوتاه بررسی‌شان می‌کنیم. برای پایتون لازم نیست از صفر شروع کنیم؛ وقت بیشتری را به Git و API/HTTP می‌دهیم.

- برنامه‌ی پایه: **۱۶ هفته‌ی آموزشی، حدود ۱۲ ساعت در هفته**؛ «هفته‌ی صفر» فقط آماده‌سازی محیط است و جدا از آن حساب می‌شود. اگر آیلتس یا زندگی شلوغ شد، ترتیب را حفظ می‌کنیم و زمان‌بندی را کش می‌دهیم.
- خروجی مطلوب: بتوانی یک LLM API را امن صدا بزنی، ابزار و RAG بسازی، کیفیت و خطاها را ارزیابی کنی، و پروژه‌ای را با مستندات و دموی قابل‌ارائه تحویل بدهی.
- پروژه را با اطلاعات عمومیِ منابع رسمی کانادا و دانشگاه‌های انتخابی‌ات می‌سازیم؛ مقررات و شرط‌های واقعی را هنگام استفاده از منبع اصلی دوباره بررسی می‌کنیم.
- این مسیر به‌تنهایی تضمین‌کننده‌ی استخدام، پذیرش دانشگاه یا مهاجرت نیست؛ اما نمونه‌کار واقعی و توانایی توضیح تصمیم‌هایت را می‌سازد.

## اولویت ابزارها — چه چیزی مهم است؟

### ضروری (به همین ترتیب)

1. **Python، خط فرمان، Git/GitHub**؛ بتوانی کد بخوانی، تغییر بدهی و نسخه‌ها را مدیریت کنی.
2. **مبانی وب و داده**: HTTP، REST، JSON، API، متغیر محیطی، SQL مقدماتی و مدل‌سازی داده.
3. **مبانی LLM**: توکن و محدودیت کانتکست، ورودی/خروجی ساخت‌یافته، هزینه و تأخیر، خطاها و محدودیت‌های مدل.
4. **Tool/function calling**: مدل ابزار را پیشنهاد می‌دهد؛ برنامه‌ی ما تصمیم می‌گیرد آیا آن ابزار مجاز است، آن را اجرا می‌کند و نتیجه را برمی‌گرداند.
5. **RAG**: جمع‌آوری و قطعه‌بندی منبع، embedding و جست‌وجو، بازیابی متن مرتبط و پاسخ همراه با منبع.
6. **ارزیابی، تست و ایمنی**: چطور بفهمیم جواب درست و مستند است، و چطور جلوی خطا، افشای کلید و prompt injection را بگیریم.
7. **تحویل نرم‌افزار**: API یا رابط ساده، لاگ، مستندات، استقرار و دموی قابل‌بازتولید.

### مفید، ولی بعد از مبانی

- **LangGraph** یا یک ابزار مشابه برای جریان‌های چندمرحله‌ای و stateful؛ ابتدا همان منطق را با پایتون ساده می‌سازیم تا معلوم باشد فریم‌ورک چه مشکلی را حل می‌کند.
- **n8n**: برای وصل کردن سرویس‌ها و ساخت workflowهای قابل‌دیدن (مثلاً webhook، زمان‌بندی و اعلان) مفید است. جایگزین فهم API، کدنویسی، ارزیابی یا طراحی Agent نیست؛ یک هفته‌ی محدود برای آشنایی و اتصال آن به پروژه کافی است.
- **MCP**: روش استانداردی برای وصل‌کردن مدل‌ها به ابزار/منابع است. بعد از فهم tool calling یادش می‌گیریم؛ در نسخه‌ی اول پروژه لازم نیست حتماً MCP server بسازیم.
- **Docker** و CI: برای اجرای تکرارپذیر و ارائه‌ی حرفه‌ای، پس از کارکردن نمونه‌ی محلی.

### فعلاً اولویت پایین

یادگیری هم‌زمان چندین agent framework، معماری multi-agent پیچیده، fine-tuning، آموزش مدل از صفر، GPU و Kubernetes. این‌ها بسته به هدف بعدی ارزش دارند، اما برای اولین نمونه‌کار معمولاً مسیر را بی‌جهت سنگین می‌کنند. ریاضی عمیق شبکه‌های عصبی هم برای ساخت اپلیکیشن‌های Agent در شروع شرط نیست؛ بعداً می‌توانیم مسیر ML را جداگانه اضافه کنیم.

## منبع بیرونی پیشنهادی: AI Engineering from Scratch

درخواست شد مسیر یادگیری را با مخزن [ai-engineering-from-scratch](https://github.com/rohitg00/ai-engineering-from-scratch) هماهنگ کنیم. این مخزن ساختار آموزشی مفیدی دارد: درس‌ها هدف، پیش‌نیاز، کد قابل‌اجرا، تمرین و مدرکِ خروجی دارند؛ اما قرار نیست همه‌ی ۵۲۳ درس و ۲۰ فاز را پشت‌سرهم طی کنیم. خود صفحه‌ی اصلی حدود ۳۴۲ ساعت و `ROADMAP.md` حدود ۳۲۳ ساعت برآورد کرده‌اند، پس از برآورد زمان هم باید با احتیاط استفاده کرد.

مسیر انتخابی برای هدف کاربردی ما:

1. **Phase 10 — LLMs from Scratch:** فقط مبانی لازم، از جمله tokenization و context؛ نه ساخت و آموزش کامل یک مدل از صفر.
2. **Phase 11 — LLM Engineering:** prompt، خروجی ساخت‌یافته، embedding/context و RAG؛ این بخش مستقیماً به Pathfinder پژوهشی کمک می‌کند.
3. **Phase 13 — Tools & Protocols:** رابط ابزار، function calling و طراحی schema؛ MCP را پس از فهم tool calling و فقط در صورت نیاز اضافه می‌کنیم.
4. **Phase 14 — Agent Engineering:** حلقه‌ی Agent، ابزارهای محدود، شرط توقف و trace؛ بعداً ارزیابی و قابلیت‌اعتماد را به آن اضافه می‌کنیم.

درس‌های مرجع در مخزن انگلیسی‌اند و صفحه‌ی اصلی می‌گوید متن انگلیسی نسخه‌ی canonical است؛ بنابراین هر درس را به فارسی توضیح می‌دهم و دستورها را برای PowerShell و پوشه‌ی تمرین Windows تو سازگار می‌کنم. مثال‌های بیرونی را پیش از اجرای واقعی می‌خوانیم؛ نام مدل‌ها و APIها را قبل از استفاده با مستندات روز provider تطبیق می‌دهیم. ادعاهای معماری مخزن را هم به‌عنوان دیدگاه آموزشی بررسی می‌کنیم، نه قانون قطعی. اصل دسترسی حداقلی، داده‌ی غیرحساس و تأیید انسان برای اقدام مهم همچنان پابرجاست.

## روش تدریس — یادگیری فعال و مرور مستند

نکته‌ات کاملاً درسته: اگر من کد کامل بدهم و تو فقط copy/paste کنی، ممکن است برنامه اجرا شود اما مفهوم جا نیفتد. در تمرین‌های قبلی هم گاهی زیادی زود کد کامل دادم؛ از این‌جا به بعد روش را عوض می‌کنیم.

هر درس این چرخه را دارد:

1. **هدف و مدل ذهنی:** اول می‌گوییم چه مسئله‌ای را حل می‌کنیم و مفهوم اصلی چیست.
2. **پیش‌بینی:** قبل از اجرا، تو می‌گویی انتظار داری کد/فرمان چه خروجی بدهد یا هر خط چه می‌کند.
3. **کد همراه با توضیح ساده و خط‌به‌خط:** هر وقت کد می‌دهم، هر خط یا بخش تازه را با زبان ساده توضیح می‌دهم: چه کاری می‌کند، چرا لازم است و خروجی‌اش چه معنایی دارد. هیچ کدی را مثل جعبه‌ی سیاه paste نمی‌کنیم.
4. **پیش‌بینی و تمرین:** قبل یا بعد از اجرا درباره‌ی خروجی سؤال می‌پرسم؛ بعد یک تغییر کوچک را خودت انجام می‌دهی تا معلوم شود مفهوم جا افتاده، نه فقط اجرا شده.
5. **کد و خروجی ASCII تا حد امکان:** متن داخل کد و خروجی ترمینال را انگلیسی/ASCII می‌نویسم تا PowerShell آن را به‌هم‌ریخته نشان ندهد؛ توضیح فارسی بیرون از code block می‌آید. اگر خود درس به پردازش متن فارسی نیاز داشته باشد، encoding را جداگانه و آگاهانه بررسی می‌کنیم.
6. **اجرا و عیب‌یابی:** خروجی را با هم می‌خوانیم و خطا را به سرنخ تبدیل می‌کنیم. اگر لازم باشد اول hint می‌دهم، نه این‌که فوراً جواب را لو بدهم.
7. **مرور پایان درس در سند همان درس:** موضوع، مدل ذهنی، فرمان‌ها/دستورهای مهم و کاربرد هرکدام، خطاهای رایج، چیزی که خودت ساختی و چند سؤال بازیابی از حافظه ثبت می‌شود.
8. **مرور کوتاه در شروع درس بعد:** چند سؤال از درس قبل می‌پرسم تا مطمئن شویم یادگیری ماندگار شده است.

پس کد را می‌گیری، ولی هر بار با توضیح، پیش‌بینی، اجرا و یک تغییر کوچک همراهش می‌کنیم. برای درس‌هایی که قبلاً تمام کردیم هم مرور را به سندشان اضافه کرده‌ام.

### بازخورد به تعریف Agent تو

نکته‌ی اصلی را درست گرفتی: Agent برای انجام یک وظیفه با کمک ابزارهاست، و دسترسی به رمزها یا کدهای API نباید بی‌حساب باشد. سه ظرافت مهم:

1. Agent الزاماً «بدون انسان» کار نمی‌کند؛ در کارهای حساس معمولاً قبل از اقدام، از انسان تأیید می‌گیرد.
2. مرز chatbot و Agent کاملاً جدا نیست: chatbot می‌تواند فقط جواب بدهد، یا پشت همان رابط چت یک Agent از ابزار استفاده کند.
3. راه امن این نیست که به Agent رمز اصلی را بدهیم. برنامه فقط ابزارهای محدود و مجاز را در اختیارش می‌گذارد؛ secret در تنظیمات امنِ برنامه می‌ماند و هیچ‌وقت داخل prompt، پاسخ یا Git قرار نمی‌گیرد.

مدل ذهنی ساده: **وظیفه → انتخاب ابزار مجاز → اجرای کنترل‌شده → بررسی نتیجه → ادامه، توقف یا درخواست تأیید انسان.**

### به‌روزرسانی امن و محیط کاری

- Python 3.14.8 در `C:\Python314` تأیید شده و بسته‌های سراسری نیز پس از به‌روزرسانی باقی مانده‌اند. برای درس‌ها، محیط مجازی جدا می‌سازیم و بسته‌ی جدید را در نصب سراسری نصب نمی‌کنیم. Python 3.14.8 آخرین patch پایدار 3.14 و یک انتشار امنیتی است ([صفحه‌ی رسمی انتشار](https://www.python.org/downloads/release/python-3148/)).
- Git نسخه‌ی `2.55.0.windows.5` گزارش کرده است؛ برای شروع دوره مناسب است و فعلاً مانعی ایجاد نمی‌کند. اگر بعدها خواستیم دقیقاً به جدیدترین نسخه‌ی منتشرشده برویم، از نصب‌کننده‌ی رسمی [Git for Windows](https://git-scm.com/install/windows) استفاده می‌کنیم.
- کدنویسی را در VS Code انجام می‌دهیم و برای فرمان‌ها از PowerShell داخلی همان برنامه استفاده می‌کنیم؛ لازم نیست فقط در پنجره‌ی جداگانه‌ی PowerShell کار کنی.

**فعلاً اجرا نکن:** `py install --update 3.14`؛ `py` تو legacy است، و نصب‌کننده خودش Python موجود را به‌روزرسانی کرده. فعلاً نسخه و packageها را بررسی می‌کنیم و نصب مجدد یا حذف انجام نمی‌دهیم.

### اولین مفهوم API

API را مثل **درِ ورودیِ قراردادی یک سرویس** تصور کن: برنامه‌ی ما یک درخواست با آدرس و نوع مشخص می‌فرستد؛ سرویس پاسخی برمی‌گرداند که معمولاً status code و داده‌ای مثل JSON دارد. در درس بعد، همین درخواست/پاسخ را با یک مثال ساده می‌خوانیم و بعد از Python صدا می‌زنیم.
