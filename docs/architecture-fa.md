# معماری Pathfinder — نسخه‌ی MVP

## هدف معماری

ساخت یک تجربه‌ی end-to-end کوچک، قابل‌تست و قابل‌گسترش برای پژوهش برنامه‌های دانشگاهی. در این نسخه قابلیت‌های اصلی deterministic هستند: داده از کاتالوگ محلی می‌آید، API آن را validate و ارائه می‌کند، و رابط React نمایش، جست‌وجو، فیلتر، shortlist محلی، مقایسه و checklist پژوهش را انجام می‌دهد.

**این نسخه LLM یا Agent نیست.** هنوز هیچ مدلی تصمیم نمی‌گیرد، ابزار خارجی را صدا نمی‌زند یا کاری را به‌جای کاربر انجام نمی‌دهد. این مرزبندی آگاهانه است: اول باید داده، provenance، تجربه‌ی مقایسه و کنترل انسانی قابل‌اعتماد شوند.

## اجزای سیستم و جریان داده

1. `backend/catalog.json` کاتالوگ کوچکِ نسخه‌بندی‌شده است. هر برنامه اطلاعات کلی، factها و فهرست منابع رسمی دارد.
2. `backend/models.py` مدل‌های Pydantic را تعریف می‌کند و ورودی کاتالوگ را هنگام بارگذاری validate می‌کند. fact تأییدشده بدون مقدار یا `source_id` مجاز نیست؛ fact ناموجود نباید مقدار ساختگی داشته باشد؛ ارجاع باید به منبعی در همان برنامه برسد؛ شناسه‌ها تکراری نیستند؛ مدت یا شیوه‌ی برگزاری‌ای که به‌صورت metadata برنامه نمایش داده می‌شود باید با fact تأییدشده و منبع‌دار منطبق باشد.
3. `backend/catalog.py` فایل JSON را بار اول می‌خواند، مدل `Catalog` می‌سازد و نتیجه را در حافظه‌ی فرایند cache می‌کند. فیلترهای API روی همین snapshot انجام می‌شوند.
4. `backend/main.py` endpointهای FastAPI را ارائه می‌کند. OpenAPI در `/api/openapi.json` و Swagger UI در `/api/docs` است.
5. `frontend/src/App.tsx` با درخواست‌های نسبی `/api/...` کاتالوگ را می‌گیرد؛ جست‌وجو و فیلتر را در داده‌ی فعلی انجام می‌دهد. جزئیات، مقایسه و ارجاع‌ها از همان داده می‌آیند.
6. Vite در توسعه، درخواست `/api` را از سمت سرور dev به FastAPI روی پورت `8000` proxy می‌کند. کد مرورگر از `localhost` برای API استفاده نمی‌کند؛ مرورگر فقط به همان origin صفحه درخواست می‌دهد.

به شکل خلاصه: **JSON کاتالوگ ← Pydantic validation ← FastAPI ← Vite proxy ← React UI**.

## فناوری و فایل‌های مهم

| فایل / پوشه | مسئولیت |
|---|---|
| `backend/catalog.json` | snapshot سه برنامه و چهار صفحه‌ی رسمی |
| `backend/models.py` | schemaها، نوع‌ها و قواعد اعتبارسنجی |
| `backend/catalog.py` | بارگذاری cacheشده و فیلتر کاتالوگ |
| `backend/main.py` | API، پاسخ‌های OpenAPI و خطاهای HTTP |
| `tests/test_api.py` | تست endpointها، فیلتر، مقایسه و provenance |
| `frontend/src/App.tsx` | صفحه‌ی محصول، modalها، جست‌وجو، shortlist، مقایسه و checklist |
| `frontend/src/types.ts` | نوع‌های TypeScript متناظر با پاسخ API |
| `frontend/src/styles.css` | طراحی واکنش‌گرا و وضعیت‌های UI |
| `frontend/vite.config.ts` | میزبان dev و proxy درخواست‌های `/api` |

## مدل داده

- **Catalog:** تاریخ بررسی کلی و فهرست برنامه‌ها.
- **Program:** شناسه‌ی پایدار، دانشگاه، عنوان، نوع برنامه، محل، metadata نمایشی و خلاصه، تاریخ بررسی، factها و منابع.
- **Fact:** شناسه، برچسب، مقدار، وضعیت، شناسه‌ی منبع، بازه‌ی اعتبار/مصرف و یادداشت.
- **Source:** شناسه، عنوان، ناشر، URL رسمی، تاریخ بررسی و نوع صفحه.

وضعیت fact یکی از دو مقدار است:

- `verified`: دارای مقدار و منبعی است که در همان برنامه موجود است.
- `not_collected`: مقدار ندارد. این مقدار به معنی «صفر» یا «ناموجود در دانشگاه» نیست؛ فقط در snapshot حاضر جمع‌آوری نشده است.

فیلدهایی مثل `summary`, `fields` و `tags` برای نمایش و دسته‌بندی‌اند؛ شرط پذیرش یا هزینه محسوب نمی‌شوند. هر ادعای پذیرش که به‌عنوان fact تأییدشده ارائه می‌شود باید در `facts` با منبع مستقل/مشخص ثبت شود.

## API و رفتار خطا

| Endpoint | رفتار |
|---|---|
| `GET /api/health` | سلامت سرویس، تعداد برنامه و تاریخ snapshot را می‌دهد. |
| `GET /api/overview` | شمار برنامه‌ها، منابع رسمی یکتا و factهای تأییدشده را می‌دهد. |
| `GET /api/programs` | کل کاتالوگ؛ `q`, `province`, `program_type`, `field` اختیاری‌اند. |
| `GET /api/programs/{program_id}` | یک برنامه؛ شناسه‌ی ناشناخته پاسخ `404` می‌گیرد. |
| `GET /api/compare?ids=...` | فقط ۲ تا ۳ شناسه‌ی متمایز می‌پذیرد؛ تعداد نامعتبر `422` و شناسه‌ی ناشناخته `404` است. ترتیب درخواستی حفظ می‌شود. |

خطای درخواست در UI به‌صورت وضعیت قابل‌فهم نشان داده می‌شود. کاتالوگ در زمان بارگذاری اعتبارسنجی می‌شود؛ خطای schema نباید به fact معتبر تبدیل یا بی‌صدا نادیده گرفته شود.

## تعاملات رابط کاربری

- فیلترهای متن، نوع برنامه و استان فقط نتایج همین کاتالوگ محدود را تغییر می‌دهند.
- Shortlist فقط شناسه‌ی برنامه‌ها را در `localStorage` مرورگر ذخیره می‌کند؛ checklist هم فقط کلید taskهای تکمیل‌شده را ذخیره می‌کند. نام، ایمیل، مدارک یا پروفایل متقاضی به سرور فرستاده نمی‌شود.
- checklist برای برنامه‌های shortlistشده از factهای موجود یادآور می‌سازد؛ مورد جمع‌آوری‌نشده مثل شهریه به task «پیداکردن صفحه‌ی رسمی» تبدیل می‌شود، نه یک مقدار حدسی. متن taskها در این MVP ثابت است؛ فقط وضعیت انجام آن‌ها محلی و برای همان نسخه‌ی بررسی‌شده ذخیره می‌شود.
- مقایسه از endpoint API می‌آید و انتخاب ۲ تا ۳ برنامه را می‌پذیرد.
- جزئیات هر برنامه fact، وضعیت جمع‌آوری، تاریخ و لینک منبع را کنار هم نشان می‌دهد.
- Escape بستن modal را انجام می‌دهد؛ `Ctrl+K` یا `Cmd+K` focus را به جست‌وجو می‌برد.
- هر مقدار جمع‌آوری‌نشده در جزئیات و جدول مقایسه با متن صریح مشخص است؛ برنامه در فهرست رتبه‌بندی پذیرش نمی‌شود.

## مرزهای اعتماد، حریم خصوصی و اختیار

- هیچ ثبت‌نام کاربر، ورود، کلید API، داده‌ی شخصی یا سند متقاضی در backend وجود ندارد.
- هیچ ارسال اپلیکیشن، پرداخت، ایمیل یا تماس خودکار انجام نمی‌شود.
- محتوا از صفحات رسمی آمده، اما ممکن است قدیمی شود؛ تاریخ بررسی و disclaimer جلوی برداشت «real-time» را می‌گیرند.
- کاربر باید هر شرط و مهلت مهم را پیش از تصمیم با دانشگاه تأیید کند.
- اگر در آینده LLM اضافه شود، مدل فقط می‌تواند بر پایه‌ی factهای بازیابی‌شده پاسخ پیشنهادی بسازد؛ پاسخ باید ارجاع داشته باشد، نامعلوم را حدس نزند و پیش از هر اقدام بیرونی تأیید انسانی بگیرد.
- اگر ابزارهای بیرونی اضافه شوند، هر ابزار باید کمترین مجوز لازم را داشته باشد و عملیات حساس پشت تأیید صریح کاربر بماند.

## تصمیم‌های MVP و مسیر گسترش

- **JSON به‌جای DB:** سه برنامه برای شروع کوچک و قابل‌بررسی‌اند؛ مهاجرت به SQLite/PostgreSQL وقتی نسخه‌بندی، هم‌زمانی یا ویرایش چندمنبعی لازم شد.
- **منبع‌نویسی دستی به‌جای scraping:** هر datum آگاهانه از صفحه‌ی رسمی بررسی شده؛ automation قبل از طراحی freshness، خطای استخراج و بازبینی انسانی اضافه نمی‌شود.
- **بدون LLM/API key:** محصول در اولین نسخه واقعاً کار می‌کند و هزینه/ریسک مدل اضافه نمی‌شود.
- **بدون رتبه‌بندی:** سلیقه‌ی کاربر یا شانس پذیرش استنباط نمی‌شود. UI ترتیب کاتالوگ را رتبه‌بندی معرفی نمی‌کند.
- گام‌های منطقی بعدی: مرور دوره‌ای و هشدار تازگی داده، افزودن scholarship/fee با منبع رسمی، schemaهای مهاجرتی، امکان افزودن یا ویرایش task شخصی در checklist و تست‌های UI. گسترش فقط وقتی انجام شود که provenance و مرزهای حریم خصوصی حفظ شوند.
