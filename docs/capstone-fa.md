# Pathfinder Canada — پروژه‌ی نمونه‌کار

**عنوان نمونه‌کار:** Pathfinder Canada — برنامه‌ی پژوهش و مقایسه‌ی تحصیلات تکمیلی با منبع رسمی و checklist محلی

> **وضعیت فعلی:** MVP اجرایی با سه برنامه‌ی واقعی و snapshot مورخ ۵ نوامبر ۲۰۲۶. اکنون تمرکز روی کامل‌کردن همین محصول است؛ درس‌های LLM/RAG و نمونه‌های toy شرط ساخت یا اجرای نسخه‌ی فعلی نیستند.

## مسئله و وعده‌ی محصول

یافتن deadline، پیش‌نیاز، شیوه‌ی پذیرش و هزینه در چندین صفحه‌ی دانشگاه وقت‌گیر است و اطلاعات تغییر می‌کند. Pathfinder یک کاتالوگ کوچک و تاریخ‌دار را برای کاربر قابل‌جست‌وجو و مقایسه می‌کند، منبع هر fact را نزدیک همان fact نگه می‌دارد و از اطلاعات جمع‌آوری‌نشده حدس نمی‌سازد.

ابزار **پژوهش را مرتب می‌کند، نه تصمیم پذیرش یا اپلای را**. وضعیت نسخه‌ی فعلی deterministic است: مدل زبانی، API key، web scraping خودکار و ارسال اقدام بیرونی ندارد.

## MVP پیاده‌سازی‌شده

- سه نمونه‌ی مستند: University of Toronto MScAC AI، Waterloo MMath Computer Science و UBC MSc Computer Science.
- جست‌وجو و فیلتر براساس متن، استان و نوع برنامه.
- صفحه‌ی جزئیات شامل fact، وضعیت، زمینه‌ی اعتبار، یادداشت و لینک منبع رسمی.
- جدول مقایسه‌ی ۲ تا ۳ برنامه؛ اطلاعات ثبت‌نشده صریحاً نمایش داده می‌شود.
- shortlist و checklist پژوهش محلی؛ taskها از factهای همان برنامه ساخته می‌شوند و وضعیت انجام فقط در مرورگر ذخیره می‌شود.
- FastAPI/Pydantic برای API و اعتبارسنجی؛ React/TypeScript/Vite برای رابط؛ pytest برای آزمون رفتار API و provenance.
- مستندات اجرا در Windows PowerShell، معماری و روش ثبت داده.

منابع، factها و caveatهای هر برنامه در [مستند داده و منابع](data-and-sources-fa.md) آمده‌اند. توضیح endpointها، schema و مرزهای اعتماد در [مستند معماری](architecture-fa.md) است.

## کاربر چگونه از MVP استفاده می‌کند؟

1. در فهرست، نام دانشگاه، حوزه یا شرط را جست‌وجو می‌کند و نوع برنامه/استان را فیلتر می‌کند.
2. جزئیات را باز می‌کند و fact را کنار صفحه‌ی رسمی، تاریخ بررسی و یادداشت خودش می‌سنجد.
3. دو یا سه برنامه را انتخاب و اطلاعات مشترک را در جدول مقایسه می‌کند؛ `Not captured` خالی‌بودن snapshot است، نه مقدار صفر.
4. برنامه‌ی موردعلاقه را به shortlist اضافه می‌کند.
5. از تب Checklist، یادآورهای متصل به factها را پیگیری می‌کند؛ مثلاً دوباره تأییدکردن intake/deadline یا پیداکردن صفحه‌ی رسمی شهریه. کاربر task را پس از خودش بررسی می‌کند؛ برنامه هیچ تماس یا اپلای انجام نمی‌دهد.

## سیاست داده و ایمنی

- مبنای factهای پذیرش فقط صفحه‌های رسمی دانشگاهی ثبت‌شده‌اند؛ هر fact تأییدشده `source_id` دارد و مدل بررسی می‌کند آن منبع واقعاً در همان رکورد باشد.
- هر برنامه و منبع تاریخ بررسی دارد. تاریخ snapshot تضمین به‌روزماندن اطلاعات نیست؛ کاربر باید مورد تصمیم‌ساز را دوباره با دانشگاه تأیید کند.
- شهریه برای هر سه برنامه جمع‌آوری نشده و بدون مقدار ثبت می‌شود.
- حداقل نمره، eligibility عمومی و گزاره‌ی funding پیش‌بینی پذیرش یا تضمین بسته‌ی مالی برای فرد نیستند.
- shortlist و taskهای تکمیل‌شده در `localStorage` همان مرورگر می‌مانند؛ هیچ پروفایل، گذرنامه، transcript، ایمیل یا secret به backend فرستاده نمی‌شود.
- اقدامات بیرونی، پرداخت و ارسال مدارک یا درخواست از محدوده‌ی محصول فعلی خارج‌اند.
- اگر بعداً LLM یا ابزار خارجی اضافه شود، باید روی داده‌ی بازیابی‌شده و citationدار کار کند، مقدار نامعلوم را حدس نزند و هر اقدام حساس را پشت تأیید صریح انسان نگه دارد.

## معماری فعلی

**کاتالوگ JSON → اعتبارسنجی Pydantic → endpointهای FastAPI → proxy نسبی `/api` در Vite → رابط React.**

فایل‌های هسته‌ای:

- `backend/catalog.json`: snapshot دستی برنامه‌ها، factها و منابع.
- `backend/models.py`: schemaها و قواعد ضد fact بی‌منبع/نامعلومِ حدسی.
- `backend/catalog.py`, `backend/main.py`: بارگذاری، فیلتر، health, overview, details و compare.
- `frontend/src/App.tsx`: explore, detail, compare, shortlist و checklist.
- `tests/test_api.py`: سناریوهای API، status codeها و اتصال هر fact به منبع.

راهنمای آماده‌سازی Windows PowerShell، تست و build در [README](../README.md) است. برای MVP هیچ secret یا API key لازم نیست.

## گام‌های بعدی، با اولویت داده و کیفیت

1. هرکدام از صفحات چهار منبع رسمی را دوباره بازبینی و تاریخ/متن factهای نیازمند به‌روزرسانی را اصلاح کن.
2. فهرست را فقط با برنامه‌های جدیدی گسترش بده که منابع رسمی و معیارهایشان قابل‌ردیابی‌اند.
3. صفحه‌های رسمی fee/tuition را جداگانه بررسی کن؛ تا زمان تأیید، وضعیت نامعلوم باقی بماند.
4. برای Checklist امکان افزودن/ویرایش reminder شخصی را بسنج؛ داده‌ها باید همچنان محلی و کم‌حساسیت بمانند.
5. پس از تثبیت جریان محصول، تست UI/accessibility و استقرار قابل‌بازتولید اضافه کن.
6. LLM، RAG، Agent یا MCP را تنها اگر نیاز واقعی محصول روشن شد، به‌صورت مرحله‌ای و با ارزیابی/تأیید انسانی بررسی کن.
